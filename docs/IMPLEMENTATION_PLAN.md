# Рабочий план реализации

Дата: 03.11.2026. План уточняет [ROADMAP](../ROADMAP.md), не меняя его gates.

## Результат анализа исходных восьми файлов

На момент исходного анализа в каталоге была только документация. Теперь добавлен каркас этапа 1; актуальная готовность — в [отчёте](STAGE_1_STATUS.md). Git-репозиторий ещё не инициализирован. Модульный монолит и PostgreSQL-очередь соответствуют объёму беты. Ключевые зависимости: интеграция требует этапов 0 и 2; настоящая аналитика — подтверждённых метрик; Telegram-доставка — членства и отзыва на всём пути.

Ожидаемые возможности источника последовательно обозначены гипотезами. Противоречий, требующих изменения объёма до каркаса, не найдено. Есть решения, которые документы намеренно оставляют открытыми:

- До identity: почтовый провайдер и политика нормализации email. Нельзя самостоятельно удалять точки или `+suffix` у адресов.
- До tenant-миграций: конкретный узкий доступ к сессии/членству до tenant-контекста и выдача lease диспетчеру. Оформить ADR и негативные тесты; не выдавать runtime обход RLS.
- До реальной аналитики: определение обращения, состав расходов, timezone, покрытие и версия CPL по доказательствам.
- До беты: объём нагрузки, инфраструктура/регион, хранение/удаление, RPO/RTO и поддержка.

## Границы каркаса

Использовать структуру ARCHITECTURE.md. Пока нет identity, API не предоставляет tenant-данные или универсальный CRUD. Health сообщает только состояние процесса; readiness проверяет необходимые зависимости с timeout и не раскрывает конфигурацию. Бот не отправляет сообщения и не начинает реальный polling автоматически. Worker не создаёт реальные сборы. Production-адаптер отсутствует; внутренний интерфейс не обещает методы провайдера.

Демосценарии, если появятся, имеют отдельный явный режим и маркировку; их нельзя загрузить в настоящую аналитику. Не создавать фиктивные интеграционные успехи и пустые миграции ради отметки о готовности.
