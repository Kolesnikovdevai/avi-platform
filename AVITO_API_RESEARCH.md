Рабочие результаты: [журнал доказательств](docs/research/EVIDENCE_LOG.md) и

При подготовке комплекта была попытка открыть официальный портал и каталог. Инструмент просмотра вернул ошибку доступа; содержимое документации не изучено. Авторизованных запросов к аккаунтам не выполнялось. Поисковые результаты и сторонние публикации не использованы как доказательства контракта.

## Официальные точки начала исследования

- [Портал разработчиков Авито](https://developers.avito.ru/).
- [Каталог API](https://developers.avito.ru/api-catalog).
- [Предполагаемый раздел авторизации для проверки](https://developers.avito.ru/api-catalog/auth/documentation) — адрес и актуальность нужно подтвердить через портал.

Эти ссылки — точки поиска, а не свидетельство доступности конкретных функций. Документацию API Авито для бизнеса и Авито Рекламы нельзя смешивать: применимость продукта, аккаунта и контракта проверяется отдельно.

## Статусы доказательств

| Статус | Значение |
|---|---|
| Не проверено | Нет прочитанной актуальной официальной спецификации |
| Описано | Найден официальный контракт, сохранены дата/версия и ссылка |
| Проверено на аккаунте | Есть воспроизводимый разрешённый тест для конкретного типа аккаунта |
| Недоступно | Зафиксирована причина: права, тариф, категория, одобрение или отсутствие возможности |
| Заблокировано | Нужны доступ, решение владельца или ответ поддержки |

«Описано» не равно «доступно всем клиентам». Результат одного аккаунта не распространяется на все тарифы и категории. Любое разрешение и изменение контракта пересматриваются при ошибках и обновлении интеграции.

## Как фиксировать результат

Для каждого ID создать запись с: ответственным, датой, официальной ссылкой/версией спецификации, продуктом API, методом и маршрутом (после подтверждения), требуемыми правами, типом аккаунта/категорией/тарифом, статусом и ограничениями. Сохранить обезличенный пример запроса/ответа без токенов, ожидаемое и фактическое поведение и вывод для PRD.

Шаблон записи:

```text
ID / дата / исследователь:
Статус:
Официальный источник и версия:
API-продукт / аккаунт-класс / права:
Проверяемая гипотеза:
Разрешённый тест, обезличенные вход и результат:
Лимиты и семантика данных:
Вывод: доступно / ограничено / недоступно / неизвестно:
Влияние на MVP и следующая проверка:
```

Временные сырые результаты держать вне репозитория, в защищённой среде с ограниченным сроком хранения. В git — только очищенные контракты и фикстуры. Отсутствие секрета в явном поле не гарантирует его отсутствия в URL, заголовках или тексте ошибки.

## План разрешённых тестов

1. Получить доступ к актуальным официальным материалам и разрешённому тестовому аккаунту. Зафиксировать необходимые одобрения для приложения.
2. Воспроизвести разрешённую авторизацию; проверить отказ при подмене state, повторном callback, истечении срока и утрате роли пользователя.
3. Проверить получение идентификатора аккаунта, доступные права, повторную авторизацию и отзыв. Refresh проверять только если он существует в контракте.
4. Прочитать небольшой набор объявлений и ограниченный исторический интервал. Проверить пагинацию и доступный диапазон без нагрузки на сервис.
5. Сверить статистику и расходы с кабинетом того же аккаунта за тот же закрытый период, часовой пояс и определения. Задокументировать расхождения, округление и задержки.
6. Повторить сбор и убедиться, что значения не удвоились. Проверить исправления данных, неполные ответы и возобновление с checkpoint.
7. Лимиты изучать по спецификации и безопасным наблюдениям; 429/сбои дополнительно моделировать локально. Нагрузочный перебор реального API не нужен.
8. При необходимости проверить второй разрешённый класс аккаунтов, а не обобщать результат первого на все сегменты.

Не пополнять счёт, не менять продвижение, не переводить средства и не управлять авансом в ходе этих тестов. Финансовые изменения требуют будущего отдельного исследования, продуктового решения и явного разрешения на конкретный тест.

## Gate перед реализацией production-адаптера

- Подтверждена пригодная для SaaS схема подключения и необходимые условия работы приложения.
- Есть официальный контракт и разрешённый тест идентификации аккаунта, статистики и расходов.
- Подтверждены совместимые гранулярность, период и определения для CPL, либо владелец явно пересмотрел объём MVP.
- Зафиксированы права, ограничения и стратегия частоты/повторов, обработка отзыва и истечения credentials.
- Принято решение, какие финансовые показатели только читаются; любые финансовые изменения выключены.
- Артефакты очищены от секретов, результаты отражены в PRD, модели метрик и схеме данных.

Если расход или знаменатель CPL недоступен, нельзя подставлять баланс, просмотры или оценку без отдельного изменения требований. Решение — остановить соответствующую функцию, согласовать меньшую бету или выбрать другой подтверждённый источник. Не компенсировать ограничение скрытым парсингом.
